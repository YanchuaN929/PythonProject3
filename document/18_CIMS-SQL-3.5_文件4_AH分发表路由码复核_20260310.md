# 文件4 AH 分发表路由码复核（2026-03-10）

## 1. 目标

- 重新按 Word 版业务规则核查文件4 `AH(责任人)`。
- 以 `example/CIMS-SQL-3.5` 为唯一数据源。
- 采用新的命中规则：
  - 责任人看 `IITF/IICS` 页面的 `分发信息`
  - 办理人若继续分发，则责任人下沉到下一级办理人
  - 若最末级办理人有多人，只要其中任一人与 Excel `AH` 匹配，即算命中

## 2. 新链路

本轮不再先假设 `DISTRIBUTERECORD.SOURCE_OBJECT_ID = 当前 IICS/IITF.id`，而是改为：

1. 从文件4 Excel 取：
   - `项目号`
   - `A(0)` `IITF/IICS`
   - `W(22)` `接口编码`
   - `AH(33)` `所内编制人/责任人`
2. 将 `W(22)` 规范化为路由码，例如：
   - `RVD PO 04 02 N B -> RVDPO0402NB`
3. 扫描 `DISTRIBUTERECORD_20260305.sql`
4. 从 `BO_TITLE` 中提取：
   - 对象类型：`IITF` / `IICS`
   - 路由码：例如 `.../IITF-RVDPO0402NB-A--接口状态...`
5. 以 `项目号 + 路由码` 对齐 Excel
6. 在每个分发对象内，用 `SENDER` 与 `OPERATOR` 关系识别最末级办理人：
   - 任何“自己又作为发送人继续向下分发”的办理人，不算叶子
   - 没有再向下分发的办理人，算叶子
7. 若叶子办理人中任一人命中 Excel `AH`，记为命中

## 3. 样本规模

- Excel `AH` 非空总行数：`41814`
- 扫描的 `DISTRIBUTERECORD` 语句数：`2372886`
- 命中外部接口且路由码可提取的分发表语句：`43769`
- 形成的分发对象组数：`5906`
- 形成的 `项目号 + 类型 + 路由码` 键数：`3790`

对比：

- Excel 中 `项目号 + 路由码` 唯一键：`8592`
- Excel 中 `项目号 + A类型 + 路由码` 唯一键：`17033`

结论：当前主要瓶颈不是“叶子多人规则”，而是 `DISTRIBUTERECORD` 中可对齐的外部接口分发表路由覆盖不足。

## 6. 关键发现

### 6.1 Word 规则正确

- 文件4 `AH` 的业务真值方向，确实是“分发信息中的最末级办理人”
- “多人叶子中任一命中即算命中”的新规则是合理的，而且已经落到 SQL 统计中

### 6.2 `CREATED_BY_ID` 不是业务真值，只是工程回退

之前的：

- `按 A 分支取 IICS/IITF.CREATED_BY_ID = 32.6176%`

它更像“对象创建/流程发起经办人”，不是 Word 语义里的“最末级办理人”。

### 6.3 当前分发表覆盖不足

- `DISTRIBUTERECORD` 里只找到了 `3790` 个 `项目号 + 类型 + 路由码`
- Excel 里有 `17033` 个 `项目号 + A类型 + 路由码`
- 因此大部分未命中来自“分发表中根本没有对应外部接口路由”，不是匹配规则写错

### 6.4 `1915` 当前是硬缺口

本轮实测：

- `DISTRIBUTERECORD` 中 `project = 1915` 且 `source_type in {ExtIITF, ExtIICS}` 的记录数为 `0`

所以：

- 文件4 `1915` 项目的责任人链，当前不可能通过 `DISTRIBUTERECORD` 闭环

## 7. 当前可落地口径

如果必须先落代码，建议顺序：

1. `项目号 + 接口编码 -> IITF 分发表 -> 最末级办理人（多人任一命中）`
2. 若 `IITF` 分发表无路由记录，再回退 `按 A 分支取 IICS/IITF.CREATED_BY_ID`

这是一条“业务真值优先，工程回退兜底”的口径。

## 8. 结论

- 文件4 `AH` 的真实业务逻辑已经定稿：看分发表最末级办理人
- 之前“只看创建人/流程人”的结论不够准确，现已被修正
- 当前 SQL 快照仍无法全量闭环，主因是外部接口分发表路由覆盖不足
- 若要继续提升命中率，下一步应继续查：
  - 为什么部分项目/路由在 `DISTRIBUTERECORD` 中根本没有 `ExtIITF/ExtIICS` 记录
  - 这些缺失路由是否落在其他分发表、文档对象或历史表中
